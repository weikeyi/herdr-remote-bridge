# Bridge Native Android — internal milestone, not a deliverable

This is a new independent native Java Android application. It does not embed a
WebView, HTML, JavaScript, PWA or the previous wrapper application. It does not
modify `android-poc` / PR 2. UI is a Reader-only session list and a manually
refreshed full text snapshot. ANSI controls are stripped; cursor movement,
alternate screens and other VT behavior are NOT emulated. Oversized snapshots
fail closed. There are no prompt, keyboard, resize, upload or mutation controls.

The native transport uses OkHttp 5.5.1 for standard-system-trust WSS and the
independent Java E2EE/chunk codecs. The dependency avoids implementing a custom
WebSocket/TLS stack. No custom trust manager, cookie jar, redirects or HTTP logging
are enabled.

Do not distribute this internal build as a finished client or substitute fake
sessions for real data. Real Windows/Core/VPS/mobile acceptance is outstanding.

## Data boundaries

- The user explicitly chooses a normalized HTTPS root origin. WSS uses that
  exact authority; invitations for another origin, plaintext, legacy bootstrap,
  unknown fields or expired/invalid keys are rejected.
- Only an enrolled Reader `CredentialRecord` is accepted by the device vault;
  invitations are never persisted. One AES-256-GCM-wrapped record is atomically
  stored in app-private `noBackupFilesDir`. Its AAD binds the configured origin.
  The non-exportable AES key is generated by AndroidKeyStore. Hardware/StrongBox
  backing is not promised. Missing/invalidated keys, corruption and authority
  mismatch fail closed without recreating the key over an existing record.
- Only the non-secret origin, device/credential IDs and origin-bound automatic
  reconnect authorization/retry state are
  stored in SharedPreferences. Android backup and
  device-transfer extraction are disabled. No credential/terminal logs, external
  storage, external invitation intents, clipboard reads or web bridges exist.
- UI invitation state saving/autofill and screen capture are disabled. Pairing
  is explicit. Backgrounding closes the connection and clears terminal/invite
  views; foreground return may recover using only previously saved Reader credentials
  after an explicit initial connection. Revocation is server-side;
  clearing local app data does not revoke a server credential.
- Java cannot guarantee erasure of immutable strings and temporary copies.
  Credential byte-array copies are wiped when their owners close; no claim that
  secrets never exist in process memory is made.

## Build/test

Pinned AGP 9.1.1, Gradle 9.3.1 (wrapper SHA-256 pinned), JDK 17,
compile SDK 37, target SDK 36, Build Tools 36.0.0, min SDK 28.
OkHttp 5.5.1 requires the newer compile SDK; this does not raise the minimum OS.
The [official AGP 9.1.1 compatibility table](https://developer.android.com/build/releases/agp-9-1-0-release-notes)
specifies this Gradle/JDK/Build Tools combination and API 37.0 support. CI installs
the exact `platforms;android-37.0` SDK package using checksum-pinned official
command-line tools 20.0. Emulator runtime stays API 36 to match target SDK.
Shared protocol sources come from `../java/src/main/java`.

```sh
./gradlew --no-daemon testDebugUnitTest lintDebug assembleDebug
./gradlew --no-daemon connectedDebugAndroidTest
```

The latter requires an isolated emulator/test device and tests only synthetic
records in unique test-owned aliases/files, never production credentials.
Unit tests cover invitation scoping, GCM tampering/wrong key/wrong authority,
typed-record rejection, strict JSON, exact session/response matching and bounded
ANSI-stripped snapshots. Synthetic client-state tests check vault-before-READY,
Reader-only finishes, unexpected frames, identity mismatch and deterministic
cleanup. They do not open a real socket or prove the full gateway lifecycle. Instrumentation
covers actual AndroidKeyStore, missing-key/no-reset behavior and AtomicFile.
Compilation alone does not prove those Android runtime properties.

## Reconnect and pairing confirmation

Each transport connection is single-use. After an explicit initial Connect or Pair,
foreground recovery creates fresh saved-credential transports and E2EE keys. The
invitation connection stores the credential, then immediately yields to a new
credential-authenticated connection before any session UI is treated as READY.
This confirms the upstream pending invitation. Invitations are never retried.
If backgrounded between persistence and confirmation, foreground return uses only
the saved credential, never the pasted invitation.

Transport drops/timeouts use at most five jittered backoffs (1, 2, 4, 8, 16 seconds,
plus up to 25% jitter) per outage. Only authenticated saved-credential READY or
an explicit user action resets the persisted retry count, not Activity recreation.
Foreground restoration also consumes the same retry budget.
Backgrounding cancels timers and closes sockets. Protocol, authentication/policy,
TLS and vault errors stop recovery. Old callbacks, selections and snapshots are
not carried into a new connection; the user selects a fresh session again.
Disconnect disables recovery until another explicit action. After explicit saved Connect validation or credential-confirmed READY, an
origin-bound non-secret reconnect flag survives Activity recreation/process death.
Disconnect, fatal errors and retry-budget exhaustion remove it. Restoring it still
requires a valid saved vault record. A pairing interrupted by process death before
first credential confirmation can resume the saved credential when the validated
ENROLLED callback persisted its identity-bound pending-confirmation marker. If the
process dies before that marker is recorded, explicit saved Connect is required.
No invitation is persisted or reused.
No persistent background service or network observer exists.
